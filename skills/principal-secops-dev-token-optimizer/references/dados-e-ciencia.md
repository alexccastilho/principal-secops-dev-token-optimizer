## Shared rules for any data project
* Raw data with personal data never goes into Git, a notebook output, a chat or a public bucket. Keep a small synthetic sample for tests.
* Credentials for databases and APIs come from environment variables or the OS keychain, never from a script, a notebook cell or an `.Rprofile` committed to the repo.
* Files from outside are hostile input: RDS, RData, `.mat`, pickle, Julia `serialize` output, notebooks and spreadsheets can carry code or break the parser. Exchange data as CSV, Parquet or JSON.
* Reproducibility is a security property: lockfile committed, exact versions, seeds fixed for anything random that feeds a decision.
* Never `rm` the raw data folder or overwrite the source file in place. Write results to a new output folder (destructive-actions rule in `SKILL.md`).

## R (tidyverse, renv, Shiny)
* Style: tidyverse style guide (style.tidyverse.org). `styler` restyles, `lintr` checks (`lintr::use_lintr(type = "tidyverse")`).
* SQL through DBI with parameters: `dbGetQuery(con, "SELECT * FROM t WHERE id = ?", params = list(id))`, or `dbSendQuery` plus `dbBind`. Placeholder depends on the backend: `?` (RMariaDB, RSQLite), `$1` (RPostgres). `glue::glue_sql()` quotes values, and identifiers written as ``{`col`}``, as a fallback when the driver has no parameters. Never `paste0()` or `sprintf()` into SQL.
* Commands: `system2(cmd, args)` with every argument passed through `shQuote()`. Never `system(paste(...))` with user text.
* `eval(parse(text = x))` on input is code execution. Use a named lookup list and reject unknown keys.
* `readRDS()` and `load()` on a file from outside: before R 4.4.0 this ran attacker code (CVE-2024-27322). R Core's advice stands on any version: use R code and data only from trusted sources. Accept only RDS/RData you produced; take CSV or Parquet from others.
* Supply chain: `renv::init()`, then `renv::snapshot()` after a change that works, `renv::restore()` on another machine. Commit `renv.lock`, `.Rprofile`, `renv/activate.R`, `renv/settings.json`. Installing a package runs its code, so check the exact name on CRAN.
* Shiny security:
  * Text reaches the page escaped by default. `HTML()` turns escaping off: never wrap user input, database text or uploaded content in it.
  * Every `input$...` is client-controlled, including values of a `selectInput` (the browser can send any value). Re-check against the allowed list on the server before using it in a query, a path or a filter.
  * `fileInput`: the file is at `input$f$datapath`; `input$f$name` is the user's file name, untrusted, never a path to write to. Upload limit is 5 MB by default; raise `options(shiny.maxRequestSize = ...)` only as far as needed.
  * Login is not part of the core `shiny` package. Authentication comes from the hosting or a proxy in front; per-user data filtering is your server code, on every reactive that reads data.
  * Errors: wrap data loading in `tryCatch()`, log the detail, show a generic message, and return no data on failure (never the unfiltered table).
* Traps and fixes:
  * CSV readers turning CPF, CEP or codes with leading zeros into numbers: declare those columns as character when reading.
  * `T` and `F` can be overwritten; write `TRUE` and `FALSE`.
  * Package attached in `.Rprofile` only on one machine: script works for the author, fails elsewhere. Declare it in the code and the lockfile.

## Julia
* Style: JuliaFormatter with a `.JuliaFormatter.toml` (`style = "blue"` or another preset). The SciML guide now points to Runic.jl; follow what the project already uses.
* Environments: `Project.toml` lists direct deps and `[compat]` bounds (including `julia`); `Manifest.toml` is the exact resolved state, generated by Pkg, never edited by hand. Commit both for an application so the exact environment can be instantiated elsewhere.
* Commands: backtick commands never go through a shell, and an interpolated `$x` becomes one argument. Safe: ``run(`convert $infile out.png`)``. Unsafe: passing user text to ``run(`sh -c $userstring`)`` or any `bash -c`.
* `Serialization.deserialize` does not validate data and its format can change between releases. Never on files from outside; use CSV, Arrow or JSON.
* Parsing and evaluating input text as Julia code is code execution. Map allowed names to functions instead.
* Errors: catch specific failures with `try`/`catch`, log, and return a refusal; never continue with a half-loaded dataset.
* Install with juliaup (julialang.org/downloads). Prefer the LTS when the project values stability.
* Traps: first call is slow (compilation), not a bug; global non-constant variables kill performance, wrap work in functions; 1-based indexing when porting from Python.

## MATLAB and GNU Octave
* MATLAB lint: Code Analyzer, `codeIssues` (R2022b+) is recommended over `checkcode`.
* Avoid `eval` and building code as text. Use dynamic field names `s.(name)`, `str2func` with a validated name, or `feval`. With user input, `eval` is code execution.
* Commands: `system(...)` runs through a shell in both (MATLAB: `cmd` or `/bin/sh` by default; Octave: `/bin/sh` or `cmd.exe`). Never concatenate user text into it; validate against an allowlist.
* `load` of a `.mat` from outside: assign to a structure (`S = load(f, "x")`) naming the variables you expect; a bare `load(f)` overwrites workspace variables with the same names.
* SQL from MATLAB or Octave: use the database interface's parameter binding, never `sprintf` of input into SQL.
* Secrets: not in `.m` files or `startup.m`; read them from environment variables.
* Octave packages run code when installed: install only packages you named, from the official index.
* Porting MATLAB to Octave: most code runs, but toolboxes, `classdef` corners and some functions differ. Test the real script; do not promise compatibility from memory.

## Fortran
* Standard: Fortran 2023 (ISO/IEC 1539-1:2023) is current, Fortran 2018 the previous edition. Compile with an explicit standard flag (gfortran `-std=f2018` or `-std=f2023`; default `gnu` accepts extensions silently).
* Compilers: gfortran (GCC), LLVM `flang` (named `flang-new` before LLVM 20), Intel `ifx`. Intel `ifort` was discontinued in late 2024; migrate to `ifx` (object and `.mod` compatible, no 32-bit targets, floating point can differ slightly: re-run numeric tests).
* Every program unit starts with `implicit none`. Modules over `COMMON` blocks; `intent(in|out|inout)` on every dummy argument.
* Debug and test builds: gfortran `-Wall -Wextra -fcheck=all -g` (backtraces are on by default), plus `-finit-real=snan` with `-ffpe-trap=invalid,zero,overflow` to catch uninitialised reals. Release builds drop `-fcheck`.
* Memory and input: array bounds overflow is the classic bug, `-fcheck=bounds` finds it. Check the status of every `open`, `read` and `allocate` and handle the error; never let a malformed input line stop with a crash mid-write.
* `execute_command_line` passes the command to the shell (`sh` or `cmd.exe`): never with input from a file or user.
* Build and deps: fpm with `fpm.toml`; pin git deps with `rev = "<commit>"`, not a branch. Formatter `fprettify` (whitespace only), linter `fortitude`.
* Legacy (FORTRAN 77, fixed form): never rewrite a working numerical code. Add a regression test with saved outputs first, then convert file by file to free form and modules, comparing results with a tolerance after each step.

## SAS
* Shell access: start sessions with `-NOXCMD` (config file or invocation only). It blocks `X`, `CALL SYSTEM`, `%SYSEXEC`, `SYSTASK` and `FILENAME PIPE`.
* Macro injection: a value typed by a user or read from data can contain `&` or `%` and be resolved as macro code. Use `%SUPERQ(varname)` to read it without resolution; never build PROC SQL text by concatenating input.
* Credentials: not in the program. Use the platform's authentication domains `PROC PWENCODE` output kept outside the code. PWENCODE only hides passwords from casual viewing: an encoded password still logs in, so protect the file that holds it.
* Traps: missing numeric values compare as smaller than any number, so `x < 10` is true for missing; test for missing first. Read the log, not only the output: NOTEs about uninitialized variables or repeated BY values in a MERGE mean wrong results without an error.
* Migration off SAS (to R or Python): run both in parallel on the same inputs and compare outputs before switching off SAS.

## Jupyter notebooks
* Outputs are saved in the `.ipynb`. A printed token, a `df.head()` with CPFs or an error trace with a connection string goes to Git with the file. Fix: `nbstripout --install` (Git filter, keeps outputs on disk only) or its pre-commit hook; for an already committed secret, rotate it, cleaning history is not enough.
* Untrusted notebooks: Jupyter's trust only stops JavaScript and sanitizes HTML in outputs you did not produce. Running a cell runs code with your permissions, trusted or not. Read every cell of a downloaded notebook before running, in a separate environment.
* `jupyter trust` only on notebooks you wrote or reviewed.
* Server: token authentication is on by default. Never disable both token and password, and never expose the server on a public address without HTTPS and auth in front.
* Secrets in cells: `os.environ["X"]` or `getpass`, never a literal, and never a magic command that sets the value inside the cell text.
* Hidden state: cells run out of order give results nobody can reproduce. Before delivering, restart the kernel and run all cells top to bottom. Move reusable code into a `.py` or `.R` module.

## pandas and Polars
* `DataFrame.query()` and `eval()` run code: never pass user text. Reference values with `@var` inside a fixed expression, or use boolean masks.
* `pd.read_pickle` on outside data executes code (see `python.md`). Use Parquet.
* Leading zeros and IDs: read CPF, CNPJ, CEP, phone and account columns as text (`dtype={"cpf": str}`; Polars `schema_overrides`). Polars infers types from the first rows only (`infer_schema_length`); a late value of another type fails the read or is mis-typed, so declare the schema.
* pandas 3.0+: copy-on-write is the only mode, so chained assignment (`df[df.a > 0]["b"] = 1`) no longer changes `df`; write `df.loc[df.a > 0, "b"] = 1`. Text columns default to the `str` dtype, so code testing `dtype == object` changes behaviour. Upgrade through 2.3 first and clear warnings. pandas 3.0 needs Python 3.11+.
* `to_sql` with `if_exists="replace"` drops the table: destructive, needs the "pode".
* Dates: pass an explicit `format="%d/%m/%Y"` for Brazilian dates; `dayfirst=True` alone only prefers day-first and is not strict. Never let `03/04` be guessed.
* Money: never float for amounts that must add up exactly; use integer cents or `Decimal`.
* Performance: vectorised operations over `apply` and row loops; Polars lazy (`scan_csv`, `.collect()`) for files larger than memory; Parquet over CSV for repeated reads.

## SQL for analytics (DuckDB and warehouses)
* Values always as parameters (`?` in DuckDB), even in internal dashboards. Table or column names chosen by a user come from an allowlist, never from the text itself.
* Parameters do not help when users write the SQL. DuckDB running untrusted SQL: `SET enable_external_access = false` (blocks file reads, `COPY`, file `ATTACH`), configure `allowed_directories` before that, then `SET lock_configuration = true`; disable `autoinstall_known_extensions` and `autoload_known_extensions`. DuckDB's docs still say this is not a sandbox.
* Read-only database user for reports and BI tools. Separate credentials per tool.
* Personal data in analytics: views exposing only the columns the analysis needs; aggregate before export.
* The database file (`mysql.md`, `bancos-outros.md` or `bancos-nosql.md`) covers engine-specific rules.

## Exporting to CSV or Excel (formula injection)
* Any text field starting with `=`, `+`, `-`, `@`, tab, carriage return or line feed can run as a formula when the file is opened in Excel or LibreOffice (OWASP CSV Injection). Full-width variants (`＝`, `＋`) count in some locales.
* Fix per text field: prefix a single quote `'`, wrap the field in double quotes and double any inner double quote. Apply only to text columns, never to real numbers, or negative values get corrupted.
* Use a CSV library for quoting; never join fields with commas by hand (a comma inside a name opens a new cell).
* Excel may strip the protection when a file is saved and reopened; the prefix stays in the data, so programs reading the file back must remove it.
* When the user reports "tudo numa coluna só" or broken accents in Excel, check the separator and the file encoding against what their Excel expects before changing data.
* For a pt-BR Windows Excel opened by double click: `;` as separator (the comma is the decimal mark there) and UTF-8 with BOM (Python `encoding="utf-8-sig"`), or deliver `.xlsx` and skip both problems. CPF, CEP and phone columns go out as text.

## LGPD in datasets: anonymization vs pseudonymization
General LGPD rules (legal basis, rights, retention, incident deadline) are in `security-baseline.md`. Data-specific points:
* Anonymized data (Art. 5 III, Art. 12) is outside the LGPD only when re-identification is not possible with reasonable effort, judged by cost, time and available technology. Reversible "anonymization" is still personal data.
* Pseudonymization (Art. 13 §4): the record can be re-linked only with extra information kept separately and controlled. Pseudonymized data is still personal data. Hashing a CPF without a secret key is not anonymization: CPFs are few enough to hash all of them and reverse it. Use a keyed hash (HMAC) with the key stored apart, or a random token table.
* Removing name and CPF is not enough: birth date plus CEP plus sex often identifies a person. Generalise (age range, first CEP digits), suppress rare combinations, aggregate small groups.
* Data used to build a profile of an identified person counts as personal data (Art. 12 §2).
* Sensitive data (Art. 5 II, for example health, racial or ethnic origin, religious belief, political opinion, genetic, biometric, sex life) needs stronger protection and a specific legal basis (Art. 11).
* Sample sentence for the user: "Tirar o nome não basta. Com data de nascimento e CEP ainda dá para descobrir quem é a pessoa. Troquei a data por faixa etária e o CEP pelos 5 primeiros dígitos."
